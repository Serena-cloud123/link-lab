# Day 6：运行组合与 32 组核对

## 今日目标

同一 RunInput 独立评估路径 A、B，返回一个 RunResult。

## 今日边界

新增 `evaluateRun`，复用 `evaluatePathA` 与 `evaluatePathB`，输出完整 `RunResult`（events、pathResults、alertCount）。不修改场景、契约与 32 行期望 CSV；不实现 API、SQLite、前端、动画或一句话解释。

## 组合规则

- events：先 A1—A3，再 B1—B5；eventIndex 固定为 0—7。
- pathResults：固定顺序为 A、B。
- alertCount：统计本次 events 中实际存在的 alert 数量。
- 路径 A 被阻断后仍须评估 B；路径 B 被阻断也不改变 A。
- presetId 只记录起始预设，不覆盖 input.conditions。
- scenarioId 与传入场景 id 不一致时，明确报错。

## AI 协作记录

原始 Prompt 要求：新增 evaluateRun 复用 evaluatePathA 与 evaluatePathB，不复制路径规则；events 按 A 后 B 拼接，保持下标 0—7；alertCount 只统计 events 上实际存在的 alert；scenarioId 不匹配时明确报错；读取冻结 CSV 对每行三列分别断言；不修改契约、场景 JSON 与 CSV。

AI 方案：evaluateRun 仅做校验、调用、拼接与计数，未在组合层判断 O/T/D1/D2，未重写告警规则。审查通过。

我补充的两点：
1. 增加 run 层级的 presetId 独立性断言——同一组 conditions 分别传 presetId "A"/"B"/"C" 与不传，断言 events、pathResults、alertCount 完全相等。原方案只有 pathB 层级的同类断言，不能排除组合函数内部动了 conditions。
2. 32 行断言时同时校验 pathResults[0].pathId === "A"、pathResults[1].pathId === "B"，确保顺序固定，不只依赖 outcome 的值。
