## 二、接口定义

### GET /api/scenarios/campus-registration
- 无参数、无路径变量，服务端只读取固定的 `../../../scenarios/campus-registration/v1.json`。
- 响应 200：场景 JSON 原样返回，含 `id`、`version`、`title`、`boundary`、`nodes`、`paths`、`initialConditions`、`defenses`、`presets`；**不含任何预填 outcome**，也不加运行结果字段。
- 契约里该字段名为 `initialConditions`（不是 `conditions`），按契约既有命名返回，不改契约。

### POST /api/evaluations
请求体（现有 `RunInput`）：

```json
{
  "scenarioId": "campus-registration",
  "presetId": "A",
  "conditions": { "O": "open", "T": "granted" },
  "defenses": ["D1", "D3"]
}
```

响应 200：直接是 `evaluateRun(scenario, input)` 的现有 `RunResult`，字段仅 `events`、`pathResults`、`alertCount`。不额外包 `runId`、`savedAt`、`saved` 等。

校验失败响应 400：Fastify 默认结构 `{ statusCode: 400, code: "FST_ERR_VALIDATION", error: "Bad Request", message: ... }`，此时不调用引擎。

## 三、输入校验方案（HTTP 边界运行时校验）

在路由上挂 body JSON Schema，校验通过后才由 handler 调用引擎：

- `scenarioId`：`type: "string", const: "campus-registration"`，必填。
- `conditions`：必填 object，`additionalProperties: false`，`required: ["O","T"]`；`O` 枚举 `open/closed`，`T` 枚举 `granted/revoked`。
- `defenses`：必填数组，`items` 枚举 `D1/D2/D3`，`uniqueItems: true`（拒绝重复），并限制长度 0—3。
- `presetId`：可选，枚举 `A/B/C`；不参与引擎判定（引擎本身已忽略）。
- 顶层 `additionalProperties: false`。
- **关键点**：Fastify 5 默认 AJV 配置含 `removeAdditional: true`，会把多余字段静默删掉而不是报 400。因此 `buildServer` 里显式设置：

```ts
Fastify({
  logger: true,
  ajv: { customOptions: { removeAdditional: false } }
})
```

并用测试实证“多余字段确实返回 400”，而不是只看 schema 声明。另会保证失败路径不进入 handler 的 `evaluateRun` 调用。

说明：`uniqueItems` 对字符串数组足够；若审查时你更希望用显式手写校验函数代替 schema 的 `uniqueItems`，我可以改成二者组合（schema 管结构 + 函数管重复），但会多一层代码。

## 二、状态设计

渲染 state（给 UI）：
- `conditions: { O, T }` —— 已提交、当前结果所代表的条件
- `preview: { O, T }` —— 滑块当前显示值（拖动中与 committed 不同）
- `defenses: DefenseId[]` —— 已提交的防御
- `presetId`, `runState`（idle/running/error/done，done 带 `input` 快照）

同步真值源 ref（避免 setState 异步导致的闭包陈旧）：
- `conditionsRef / previewRef / defensesRef / presetIdRef / scenarioRef` —— 与对应 state 同步写入
- `submittedConfigRef` —— 最近一次提交配置的序列化字符串，用于去重
- `runVersionRef` —— 单调递增请求版本号，回写前比对，丢弃过期响应
- `mountedRef` —— 组件卸载门禁

"从预设 X 调整"派生：`conditions !== preset.conditions || defenses.length > 0` 时显示该提示。

## 三、何时发 POST

POST 只有三个入口，全部收敛到单一函数 `run(nextConditions, nextDefenses)`：

1. **滑块提交** `commitConditions()`：`onMouseUp / onKeyUp / onTouchEnd / onBlur` 触发。读取 `previewRef`，与 `conditionsRef` 比较。
2. **防御点击** `toggleDefense(d)`：直接算出新数组，调用 `run(conditions, nextDefenses)`。
3. **手动运行** `runCurrent()`：调用 `run(conditions, defenses)`（供切预设后跑基线，允许重跑相同配置）。

**不**通过 `useEffect` 监听配置变化发 POST。选预设不自动 POST。

`run()` 内部：`running` 守卫 → `version = ++runVersionRef` → 同步更新 refs/state → 显式构造 `input = { scenarioId, presetId, conditions: nextConditions, defenses: nextDefenses }`（**不**依赖刚 setState 后可能未更新的值）→ `postEvaluation(input)` → 回调里 `if (runVersionRef.current !== version) return;` 再写结果/错误。

运行中禁用：预设按钮、滑块、防御开关、运行按钮全部 `disabled`。

## 四、一次拖动最多一次请求

- 拖动过程只 `onInput` 改 `preview`，**不**调 `run`。
- 松手时 `commitConditions`：若 `preview === conditions`（回到原值/未改）→ 直接 return，0 次 POST。
- 若值改变：再比对 `submittedConfigRef`，若已提交过该配置 → return（防 `mouseup`+`blur` 连续触发重复提交）。
- 通过后才 `run()`，`run` 内部同步把 `conditionsRef` 设为新值。因此随后的 `blur` 再进 `commitConditions` 时 `preview === conditions`，自然 return。
- 这两道门保证"一次拖动最多一次"和"松手为原值零次"。

## 五、防止旧响应覆盖新配置

- `runVersionRef` 单调递增；每个 POST 拿到自己的 version，`then/catch` 回写前校验 `version === runVersionRef.current`，不匹配直接丢弃。
- `run()` 同步把 refs 更新为本次配置，后续用户操作产生的新请求会更新 version，旧响应自动失效。
- 运行中所有会改配置的控件 `disabled`，杜绝并发修改。
- 失败时 `runState` 置 `error`（显示失败与重试），**不**保留上次 done 结果冒充本次。

## 二、基线快照数据结构

```ts
interface BaselineSnapshot {
  scenarioId: string;
  scenarioVersion: number;
  conditions: { O: OValue; T: TValue }; // 同条件依据
  input: RunInput;      // 原样保存该次真实请求（defenses 恒为 []）
  result: RunResult;    // 该次真实响应
}
```

状态：

```ts
type BaselineState =
  | { status: "idle" }
  | { status: "running" }
  | { status: "error"; message: string }
  | { status: "done"; snapshot: BaselineSnapshot };
```

配套 refs：`baselineVersionRef`（单调递增）、`baselineInFlightRef`（一次点击只发一次）。
资格判定（仅这四项，不含 `presetId`）：
`snapshot.scenarioId === scenario.id && snapshot.scenarioVersion === scenario.version && snapshot.conditions.O === conditions.O && snapshot.conditions.T === conditions.T`。

自动捕获：`run()` 成功且 `nextDefenses.length === 0` 时，用**该次真实 input+result** 写入基线（不从干预结果反推）；同时 bump `baselineVersionRef`，使更早在途的基线响应作废。

## 三、何时失效

1. **O 或 T 变化**：在 `run()` 里比对新旧 O/T（`conditionsRef` 提交前快照），一旦变化立即 `baselineVersionRef++`、`baselineInFlightRef=false`、`setBaselineState(idle)`。
2. **切预设**：`handleSelectPreset` 内同样立即失效（与 Day 9 的零自动 POST 一致）。
3. **场景重载**（id/version 变）：失效。
4. **迟到响应**：基线响应回来时要求 `version === baselineVersionRef.current` 且 `key === 当前 O/T+场景`，否则直接丢弃，绝不恢复。
5. **只切换防御（O/T 不变）**：**不失效**，同条件基线继续用于对比。

## 四、补跑基线如何不改变当前运行

- `runBaseline()` 用**当前 scenarioId / 当前 O/T / `defenses: []`** 显式构造 input，只写 `baselineState`，**完全不触碰** `conditionsRef`、`defensesRef`、`submittedConfigRef`、`runState`。
- 不重置 D1/D2/D3 开关；不覆盖已有当前干预 `RunResult`；结果面板始终渲染 `runState`（当前运行），基线只在对比区以「无防御基线」独立标注，绝不冒充当前配置。
- 防护：`if (baselineInFlightRef.current || runningRef.current) return;`，一次点击一次 POST。按钮仅在 `defenses.length > 0` 且无有效基线时出现，运行中禁用。

## 五、两条请求轨道的防乱序（对应要求 7）

| | 当前运行 | 补跑基线 |
| --- | --- | --- |
| 入口 | `run()`（Day 9 唯一入口） | `runBaseline()` |
| 版本闸 | `runVersionRef` | `baselineVersionRef` + key 校验 |
| 关联 input+result | `runState.done{result,input}` | `BaselineSnapshot{input,result}` |
| 写入目标 | 只写 `runState` | 只写 `baselineState` |

两个集合互不相交，跨轨道的乱序响应无法互相覆盖。基线运行**不**禁用配置控件（这样 O/T 改动可自然使在途基线作废，正是要求 4 语义）；当前运行进行中则沿用 Day 9：配置控件与基线按钮均禁用。

## 二、eventIndex 状态设计

```ts
const [eventIndex, setEventIndex] = useState(0);
const [playing, setPlaying] = useState(false);
```

- 唯一数据源：`runState.status === "done" ? runState.result.events : []`；不缓存副本。
- 下标始终 `clamp(0, events.length - 1)`；`events.length === 0` 时恒为 0，播放条整体禁用并显示「暂无事件」。
- 「播放」在 A 段只做**下标按 800ms 自动 +1**，到 7 自动停；不做任何流线运动、回弹、脉冲、过渡（B 段才做）。
- 暂停/上一步/下一步/跳转都暂停播放；上一步、下一步在两端禁用。
- 计时器用 `useEffect([playing, lastIndex])` 内 `setInterval`，返回 cleanup；组件卸载、暂停、重置、换配置都会清掉，不会残留定时器。
- 重置统一走一个 `resetPlayback()`（`setPlaying(false); setEventIndex(0)`），只在四处调用：
  1. `run()` 发起请求时（覆盖 O/T 提交、防御切换、手动重跑）；
  2. `run()` 收到 `done` 时（幂等再置 0，对应「新响应到来」）；
  3. `handleSelectPreset()`；
  4. `loadScenario()` 重载场景。
- `runBaseline()` 属独立轨道，**不**重置播放，不打断当前事件的阅读位置。
- 播放只改下标，不发任何 POST；上一步/下一步/跳转同理。

## 三、静态图状态如何从 events 派生

`derivePlaybackView(result, index)` 只做取值与映射，不判断路径成败：

```ts
event = result.events[clamp(index)]
edgeId = `${event.fromNodeId}->${event.toNodeId}`
alertNodeId = event.alert?.interfaceNodeId ?? null
arrivedNodeId = event.outcome === "data-arrived" ? "N7" : null
unmetReasons = event.conditionChecks.filter(c => !c.satisfied)
priorRejected = result.events.slice(0, index)
  .filter(e => e.outcome === "rejected" && e.pathId === event.pathId).at(-1) ?? null
```

`ScenarioGraph` 对**当前事件那一条物理边**套状态，其余边保持底图中性：

| 当前 outcome | 边 | 节点 | 必备文字 |
| --- | --- | --- | --- |
| passed | 该 `from→to` 边实线高亮 + 标签 `A1 · 已通过` | from 节点 visited | 面板显示步骤/起终/条件检查 |
| rejected | 该边虚线红 + 标签 `A3 · 被拒检查点`（标签默认落在边中点，即检查点位置） | 不把 N7 误标成被拦 | 面板「被拒位置：N3 → N7 检查点（D1）」+ 所有 `satisfied=false` 的 reason |
| skipped | 该边不套高亮，保留底图连线，只加灰色标签 `B3 · 未执行` | 无 | 面板「未执行」+「此前被拒：B2（原因…）」 |
| data-arrived | 该边成功高亮，标签 `A3 · 已到达` | `N7` 加 `arrived` 徽标 | 面板「报名明细已到达（模拟）」 |
| 带 alert | 主流线状态**不变** | `alert.interfaceNodeId` 加告警徽标 | 面板「检测到敏感请求，未自动阻断」+ 引擎 `alert.reason` |

**A1/B1 区分**：边的物理 id 仍是 `N1->N2`，但当前事件只取 `event.pathId + event.stepId` 生成标签与 class，所以第 0 条显示 `路径 A · A1 · 已通过`，跳到第 3 条显示 `路径 B · B1 · 已通过`；底图的 `A1 / B1` 只作为未选中时的底图标签，永远不会把两个步骤合成一个高亮。图下固定一行：`当前事件：路径 A · A1（已通过）`，便于直接核对。

## 二、动画取消机制

**单一来源**：React 的 key 强制 remount。

- 所有动画元素（active edge 的 CSS 动画、alert 侧向脉冲 overlay）挂在一个 wrapper 上，wrapper 的 key = `${runVersionRef.current}-${eventIndex}-${animationsEnabled}`。
- `runVersionRef` 在 `run()`、`handleSelectPreset()` 时已 bump（继承 Day 9/10 设计），因此：
  - 暂停/上一步/下一步/跳转 → `eventIndex` 变 → key 变 → 旧动画 DOM 卸载，新动画从零开始
  - 切预设 / O/T / 防御 / 新响应 → `runVersionRef` bump + `eventIndex` 已被 `resetPlayback()` 置 0 → key 变 → 同上
  - 关动画开关 → `animationsEnabled` 变 → key 变 → 同
- 这比手动清 setTimeout/RAF 更彻底：所有 CSS keyframes、transition、SVG 动画在 DOM 节点卸载瞬间全部终止，不残留任何定时器。
- **不使用** `requestAnimationFrame` / `setTimeout` 驱动业务逻辑。播放条推进下标的 800ms 间隔已存在（A 段），CSS 时间 **只** 决定视觉过渡，不决定业务下标。

## 三、关闭动画与 prefers-reduced-motion 的处理

1. **初始值**（`App.tsx`）：
   ```
   reduced = window.matchMedia("(prefers-reduced-motion: reduce)").matches
   persisted = localStorage.getItem("animationsEnabled")
   default: persisted === "false" ? false : reduced ? false : true
   ```
2. **切换动画按钮**（PlaybackBar）：直接 setAnimationsEnabled + 持久化 localStorage。
3. **DOM 选择器隔离**：`<body class="animations-enabled">`（或 `.app-root.animations-enabled`）上挂载一个全局 class；所有 CSS keyframes 都包在 `.animations-enabled .graph-edge-active.graph-edge-passed { animation: ... }` 下。关动画时，所有 outcome 的静态样式（stroke/dasharray/badge/arrived/alert）**保持不变**，只是 animation 属性为 none。
4. **系统设置变化监听**：一个 `useEffect` 订阅 `matchMedia` 的 `change` 事件，系统改为 reduce 时自动关；用户手动开启后覆盖系统默认。
5. **ReactFlow 自带 animated 字段**：A 段已将所有 edge 的 `animated` 字段置 `false`，B 段不改变这个字段，动画完全由 CSS keyframes 驱动，不依赖 ReactFlow 的 built-in 动画（ReactFlow 动画在关浏览器动效时仍会执行，与 CSS keyframes 行为不同）。
